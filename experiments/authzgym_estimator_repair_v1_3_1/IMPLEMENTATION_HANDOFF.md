## Step 1 -- Read-only harness that reproduces the preserved baseline

**Add:** `src/ser/evaluation/authz_v1_3_1_harness.py`,
`tools/run_estimator_repair_study.py`,
`tests/test_estimator_repair_harness.py`,

**Protected:** everything in section 0. In particular the harness must *import*
`ser.evaluation.authz_v1_3` and `ser.authzgym.policies` for the B0 baseline; it
must not modify them.

**Behavior:**

- Load the development public population, development restricted population,
  development annotations, development transformation maps, and the public
  contract.
- Reproduce the frozen oracle diagnostic path exactly as
  `tools/validate_authzgym_v1_3_oracle.py --split development` does: gold
  response from annotation, empty initial state, fixed adapter, unchanged
  estimator, ranking by `(-value, canonical ordinal ascending)`.
- Expose a pluggable component interface with two operations only:
  `component_values(sealed_input) -> {target_slot: float}` and
  `component_declared_ties(sealed_input) -> [[target_slot, ...], ...]`.
  Every baseline and every candidate is expressed through this interface.
- Compute: canonical aggregates (top-1, top-2, mean normalized regret, illegal
  count, discriminating/nondiscriminating counts); section-14 action-value
  equivalence over the 5 equivalence variants; the new own-ranking invariance
  check of preregistration section 2.6; the `longest_artifact` read-out; the
  degeneracy census; family-macro summaries; leave-one-source-out folds.
- Write the first `ACCESS_LEDGER.jsonl` record: study start, actor, motivation

  recorded in ORACLE_BLOCKER.md"), and the repository commit hash.
- Implement a filesystem allowlist that **fails closed** on any path matching
  `*CONFIRMATION*` or `*confirmation*` under the v1.3 directory.

**Tests:**

- `test_baseline_reproduction`: B0 canonical top-1 `== 0.625`, top-2 `== 0.875`,
  mean normalized regret `== 0.175` (within `1e-12`), illegal count `== 0`,
  section-14 equivalence `40/40` with zero failures.
- `test_longest_artifact_readout`: B0 `longest_artifact` top-1 `== 0.125`,
  top-2 `== 0.375`, regret `== 0.7833...` within `1e-12`.
- `test_own_ranking_invariance_baseline`: B0 own-ranking invariance is `36/40`,
  with the 4 mismatches occurring in `artifact_identifier_variation` and
  `combined_permutation` for exactly the two ownership-family sources. This is a

  a defect to fix in `policies.py`.
- `test_selection_metric_arity`: the selection-metric entry point raises unless
  it receives exactly 8 case ids, all with `variant == "base_entry"`.
- `test_confirmation_paths_blocked`: every forbidden path in preregistration
  section 3.3 raises on open.
- `test_protected_hashes_unchanged`: all section-0 hashes match.

**Artifacts:** `BASELINES.json` (B0 block only at this step),
`ACCESS_LEDGER.jsonl`.

## Step 2 -- Sealed component input and the allowlist checker

**Add:** `src/ser/evaluation/authz_v1_3_1_sealed_input.py`,
`tests/test_estimator_repair_sealed_input.py`.

**Protected:** section 0.

**Behavior:**

- Implement `SealedComponentInput`, an immutable object exposing exactly the
  seven items of preregistration section 2.4 and nothing else. Any other
  attribute access raises `ForbiddenComponentInput`.
- The sealed input is constructed from the public case and the response only. It
  never holds a reference to the restricted case, the annotation record, the

- Deliberately exclude `line_count`, `public_id`, `path`, `exported_symbols`,
  candidate `public_label`, and inventory array order from the exposed surface.

**Tests:**

- one test per forbidden name class: hidden roles, mechanism ids, retired
  labels, restricted ordinals, evaluator metadata, confirmation identifiers,
  surface statistics;
- attribute access outside the allowlist raises;
- the sealed input holds no reference reaching restricted data (object graph
  walk);
- a deliberately non-conforming fixture module is rejected by the static
  checker.

**Artifacts:** none beyond test fixtures.

**Acceptance:** all tests pass; the static checker rejects every negative
fixture and accepts a minimal conforming fixture.

**Stop if:** the seven allowlisted items are insufficient to express even
baseline B2 (category-match floor). That would be a contradiction in

## Step 3 -- Compute the information ceiling, before any candidate exists

**Add:** `tools/compute_authorized_information_ceiling.py`,
`tests/test_estimator_repair_ceiling.py`.

**Protected:** section 0.

**Behavior:**

- **Tier 1.** For each of the 8 canonical development cases, partition the legal
  targets into classes by identical category vector (the `r0..r4` boolean tuple).
  Enumerate all orderings over classes. Within a class, apply the frozen
  evaluator tie-break (ascending canonical ordinal). For each case record whether
  some class ordering attains top-1, and whether some attains top-2. Average over
  the 8 cases to obtain `tier1_top1_ceiling` and `tier1_top2_ceiling`. Also
  record the per-case class structure and the size of the class containing each
  maximum-usefulness target.
- **Tier 2.** Accept a declared feature map `phi` (a callable over the sealed
  input). Group the 8 cases by identical `(phi(case), class structure)`
  signature. Enumerate class orderings subject to the constraint that cases in
  the same signature group receive the same ordering rule. Report the best
  achievable average. Tier 2 is computed per candidate in steps 7--9 and is not
  run at this step beyond its unit tests.
- Write `INFORMATION_CEILING.json` containing both tiers' definitions, the Tier-1
  results, the per-case class structures, and the decision.

**Tests:**

- hand-constructed 3-target fixtures with known ceilings;
- a fixture where all targets share one class -> ceiling equals whatever the
  ordinal tie-break yields;
- a fixture where every target is its own class -> ceiling is 1.0;
- Tier-2 correctly collapses two cases with identical signature.

**Artifacts:** `INFORMATION_CEILING.json`.

**Acceptance:** the tool is deterministic across two runs and matches all
hand-calculated fixtures.

**Decision gate (blocking, consumes no budget):** if
`tier1_top2_ceiling < 0.80` or `tier1_top1_ceiling < 0.60`, write the outcome
`authorized-information-insufficient` to `DEVELOPMENT_REPORT.json`, write
`STUDY_BLOCKER.md`, and **stop the study**. Write no candidate. Go to step 10
for the report and then step 11.

## Step 5 -- Invariance and degeneracy instrumentation

**Add:** `tests/test_estimator_repair_invariance.py`; extend the harness.

**Protected:** section 0.

**Behavior:**

- Implement the section-2.6 own-ranking invariance check: for each source,
  compute the component's own full ranking on `base_entry` and on each of the 5
  equivalence variants, map every ranking through
  `canonical_ordinal_by_variant_public_id` (evaluator channel, harness only),
  and compare. Report `n/40`.
- Implement the strict non-degeneracy certificate: per case, whether the value
  vector has a strictly unique maximum. Report the count over 8 canonical cases.
  This count is the quantity compared against `nd3_floor_from_b2` for ND-3, and
  it is also reported alongside the strictly-unique-second count as a descriptive
  statistic.
- Implement ND-1 (no case in which all legal targets share one common value) and
  ND-2 (the argmax set of each case is contained in one category-vector
  equivalence class, using the step-3 Tier-1 class structure).
- Implement tie-dependence: per case, whether removing the evaluator ordinal
  tie-break would change the top-1 or top-2 outcome. Reported only; not a gate.
- Implement leave-one-source-out: 8 folds, section-4.2 gate recomputed on 7
  sources. Reported only; not a gate.

**Tests:**

- synthetic components with known invariance properties;
- the B0 regression fixture from step 1 (`36/40`) still holds;
- a component that reads the slot index to break ties is detected as
  non-invariant under `artifact_reordering`;
- a constant-valued component fails ND-1 in every case;
- a component whose argmax set spans two different category-vector classes fails
  ND-2, and one whose argmax set is a two-target tie inside a single class
  passes it.

**Artifacts:** instrumentation is reported inside every candidate record.

**Acceptance:** all tests pass; instrumentation is deterministic.

`src/ser/evaluation/authz_v1_3_1_adapter.py` (the current candidate), copied on

`experiments/authzgym_estimator_repair_v1_3_1/candidates/est-repair-v1.3.1-A-<k>/`

**Behavior, per candidate, in this exact order:**

   rule or a development-observed structural defect. For `k >= 2` it must cite a
   mechanism-level defect of candidate `k-1`. Append it to
   `CANDIDATE_LEDGER.jsonl` **before** evaluation.
2. Reject the attempt without consuming budget if the rationale cites a score, a

3. Implement the component against the sealed input.
4. Run the step-6 firewall suite and the step-2 static checker. A failure here is
   an implementation defect, not a spent attempt; fix and re-run freely.
5. Compute the complexity score (preregistration section 4.8). If `> 4`, the

6. Compute the Tier-2 ceiling for the candidate's declared feature map.
7. **Evaluate the section-4.2 gate exactly once** -- the frozen thresholds, the
   invariance and allowlist certificates, and ND-1/ND-2/ND-3 against the frozen
   `nd3_floor_from_b2`. The candidate is now spent.
8. Record: component hash, rationale, complexity score, Tier-2 ceiling, canonical
   metrics, ND-1/ND-2/ND-3 outcomes, degeneracy certificate, tie-dependence

**Tests:** the candidate must pass the full step-5 and step-6 harness batteries

## Blocking semantic ambiguities -- stop immediately, do not decide

Stop and write `STUDY_BLOCKER.md` if any of these occurs:

1. A published v1.3 rule admits two readings that produce different component
   outputs on any development case.
2. The seven allowlisted inputs of preregistration section 2.4 are insufficient
   to express a baseline the plan requires (B1 or B2).
3. Baseline B0 does not reproduce the recorded development figures exactly.
4. Baseline B0 fails any component-firewall check, implying the preserved
   action-value path consumes privileged information.
5. The section-14 transformation-equivalence check and the new section-2.6
   own-ranking check disagree for a candidate in a way that cannot be reported
   as two separate, both-correct measurements.
6. The frozen tie rule cannot be applied because a candidate emits a value that
   is not a finite float, or emits a target outside the legal set.
7. The complexity score cannot be computed unambiguously for a candidate's
   structure.
8. Any protected file's hash changes.
9. Any confirmation path is accessed, by any process, at any point.
10. Executing a step would require choosing a new label meaning, syntax rule,
    transformation, threshold, population rule, metric, weighting, or access
    condition.

Implementation inconvenience, a candidate scoring below a threshold, a
disappointing ceiling, or the absence of a passing candidate are **not**
ambiguities and are **not** permission to choose new semantics. They are
results, and they are reported as results.
